# План внедрения автопроверки решений

Основан на `docs/auto-check-design.md`. Привязан к реальному коду (проверено 07.07.2026).
Контекст сроков: MVP к 01.08.2026, пилот с 11-м классом с сентября.

## Предпосылки и один блокер

⚠️ **Блокер: схема Prisma опережает миграции.** В `prisma/schema.prisma` уже есть немигрированные модели (`Lesson`, `Test*`, `StudentProfile`, `TopicMastery` и др.). Любой `prisma migrate dev` сейчас сгенерирует миграцию со ВСЕМИ этими таблицами разом. Перед этапом 1 нужно решить:

- **Вариант А (рекомендую):** смигрировать накопившееся отдельной осознанной миграцией сейчас, потом чистая миграция под автопроверку.
- **Вариант Б:** добавить `SolutionSubmission` в schema и принять, что миграция потащит всё вместе (проверить на копии БД).

Также учесть: существующий upload-роут `app/api/teacher/uploads/route.ts` — **только для учителя**. Ученикам нужен свой роут (этап 1), нельзя просто переиспользовать.

## Этап 0 — Подготовка (0.5 дня)

1. Разрулить блокер с миграциями (см. выше), прогнать на копии прод-БД.
2. Завести ключ API (рекомендация: OpenRouter — одна интеграция, смена моделей без релиза).
3. Env: `AI_CHECK_ENABLED`, `AI_CHECK_API_KEY`, `AI_CHECK_MODEL` (старт: Claude Sonnet 4.6), `AI_CHECK_FALLBACK_MODEL`, `AI_CHECK_MAX_CONCURRENCY=1`.
4. Собрать «золотой набор»: 15–25 реальных фото решений (верных, с ошибками, нечитаемых) — для проверки промпта на этапе 2.

**Готово, когда:** миграции чистые, ключ работает, золотой набор лежит в отдельной папке (не в repo).

## Этап 1 — Сдача решений без ИИ (2–3 дня)

Ценность сама по себе: учитель видит фото решений учеников.

1. **Prisma:** модель `SolutionSubmission` (+ enums `SubmissionStatus`, `SubmissionVerdict`) — поля из design-doc; связь с файлами через join-таблицу `SolutionSubmissionFile` (у `StoredFile` уже 3 именованных relations, не перегружать). Миграция + `db:generate`.
2. **API загрузки для ученика:** `app/api/student/solutions/route.ts` (POST, multipart) — по образцу teacher/uploads: `tryGetCurrentUser` (STUDENT), `saveUploadedFile()` → `prisma.storedFile.create` → `SolutionSubmission(PENDING)`. Лимиты: ≤3 файла, ≤5 МБ, jpg/png/pdf. Rate limit: `enforceApiRateLimit(request, "api:student-solutions", user.id, 10, 60*60_000)`.
3. **Доступ к файлам:** расширить `lib/file-access.ts` — ученик видит свои сабмиты, учитель все. Обновить `lib/stored-files.ts` (`countStoredFileUsages` — учитывать новую связь!).
4. **GET-эндпоинты:** список сабмитов по номеру (ученик — свои, учитель — по студенту).
5. **UI:** в `components/student-single-number-card.tsx` — блок «Отправить решение» (загрузка, список отправленного). У учителя в деталке ученика — фото сабмитов.
6. Ревалидация: `revalidateStudentTopicsData()` + `revalidateTeacherStudentsData()` + `revalidatePath`. Лог: `solution.submit.succeeded`.

**Готово, когда:** ученик отправляет фото, учитель их видит; lint/test зелёные; чужие сабмиты недоступны (проверить руками под двумя аккаунтами).

## Этап 2 — Модуль проверки (3–4 дня)

1. **`lib/solution-check.ts`:** сборка промпта (`conditionLatex` + `answerLatex` + фото), вызов модели, tool-call/JSON-схема ответа (`verdict, recognized_answer, transcription, error_location, comment, confidence`), 1 ретрай на невалидный JSON, fallback-модель, учёт токенов. Промпт: сначала дословная транскрипция (не «исправлять» описки ученика при чтении!), принимать любой корректный метод решения, при нечитаемости — `UNCERTAIN`. Комментарии по-русски.
2. **`lib/solution-check-queue.ts`:** in-process очередь, concurrency 1, статусы `PENDING → CHECKING → DONE/FAILED`. При старте процесса подбирать зависшие `CHECKING` (рестарт pm2!) обратно в `PENDING`.
3. **Прогон на золотом наборе** скриптом (`scripts/check-golden-set.ts`), ручная сверка вердиктов. Цель: ≥85% верных вердиктов, 0 ложных GREEN на наборе. Итерации промпта до достижения.
4. **Тесты** (`tests/solution-check.test.ts`): парсинг ответа модели, маппинг вердикт→предлагаемый статус, обработка мусорного JSON — чистая логика без сети, как принято в repo.

**Готово, когда:** золотой набор проходит порог; тесты зелёные. Юнит `lib/` без DB/сети — конвенция repo.

## Этап 3 — Интеграция в продукт (2–3 дня)

1. Автозапуск проверки после POST сабмита (если `AI_CHECK_ENABLED`).
2. **Результат в UI ученика:** спиннер «Проверяется…», затем вердикт + комментарий (KaTeX), кнопка «Повторить» при `FAILED`. Live-обновление: `publishDashboardRealtimeEvent({ kind: "student-progress-changed", studentId, topicId })` — существующий листенер подхватит.
3. **Предложение статуса:** `CORRECT` → кнопка «Отметить зелёным» (ученик подтверждает, идёт через существующий `app/api/student/topic-status/route.ts`), `INCORRECT` → предложение YELLOW, `UNCERTAIN` → бейдж «нужна проверка учителем».
4. **Вид учителя:** в деталке ученика — сабмиты с фото, транскрипцией, вердиктом ИИ и confidence; возможность пометить вердикт как ошибочный (поле `teacherOverride` — данные для оценки точности).
5. Логи: `solution.check.started/succeeded/failed/uncertain` + токены и стоимость в записи.

**Готово, когда:** полный цикл ученик→ИИ→вердикт→статус работает на dev и на VPS; lint/test зелёные.

## Этап 4 — Пилот и калибровка (2–4 недели, сентябрь)

1. Первые 2 недели: учитель сверяет **все GREEN-вердикты** (ложный GREEN — главный риск) и выборочно остальные, отмечает ошибки ИИ через `teacherOverride`.
2. Еженедельно: срез точности (доля верных вердиктов, доля UNCERTAIN, стоимость/проверка) — простой SQL или страничка статистики.
3. По итогам: подстройка промпта, решение про модель (даунгрейд на дешёвую, если точность позволяет; эскалация сложных случаев).
4. Критерий успеха пилота: ≥85% верных вердиктов, <2% ложных GREEN, ≤10% UNCERTAIN.

## Сводка

| Этап | Что даёт | Оценка |
|---|---|---|
| 0. Подготовка | миграции, ключ, золотой набор | 0.5 дня |
| 1. Сдача решений | учитель видит фото ДЗ | 2–3 дня |
| 2. Модуль проверки | ИИ-вердикт офлайн, качество измерено | 3–4 дня |
| 3. Интеграция | полный цикл в продукте | 2–3 дня |
| 4. Пилот | реальная точность, калибровка | сентябрь |

Итого разработки: **~8–10 рабочих дней** → при старте сейчас этапы 0–3 укладываются до 01.08 с запасом. Если MVP-скоуп поджимает — в MVP можно взять только этапы 0–1 (сдача решений), а ИИ-проверку включить флагом `AI_CHECK_ENABLED` позже без нового релиза схемы.

## Риски исполнения

- Немигрированная схема — разрулить ДО любой новой миграции (этап 0, вариант А).
- In-process очередь теряет `CHECKING` при рестарте pm2 → обязательный recovery при старте (этап 2.2).
- `countStoredFileUsages` не знает про новую связь → файлы сабмитов могут удалиться как «неиспользуемые» (этап 1.3).
- Ложные GREEN → сверка на пилоте, порог confidence, транскрипция в промпте.
