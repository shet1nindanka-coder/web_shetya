# Автопроверка решений учеников — проектный документ

Дата: 07.07.2026. Вводные: ученики сдают **фото рукописного решения**, нужен **вердикт + указание места ошибки**, объём **до 500 проверок/мес**, доступ к зарубежным API есть.

## 1. Как это работает (флоу)

1. Ученик на странице темы нажимает «Отправить решение» у конкретного номера, прикладывает 1–3 фото (jpg/png/pdf — типы уже разрешены в `lib/utils.ts`).
2. Файл уходит через существующий механизм pre-upload → `lib/storage.ts` → `StoredFile`.
3. Создаётся запись `SolutionSubmission` со статусом `PENDING`, проверка запускается асинхронно (in-process, как realtime pub/sub — у нас один инстанс на VPS, этого достаточно).
4. Воркер собирает промпт: `conditionLatex` + `answerLatex` номера + фото → отправляет в vision-модель, требует **строго структурированный JSON** (tool call / structured output):

```json
{
  "verdict": "CORRECT | INCORRECT | UNCERTAIN",
  "recognized_answer": "…",
  "error_location": "шаг/строка, где ошибка, или null",
  "comment": "1–3 предложения по-русски",
  "confidence": 0.0
}
```

5. Результат пишется в `SolutionSubmission`, ученику прилетает по SSE (`lib/dashboard-realtime.ts`), комментарий рендерится с KaTeX.
6. Статус светофора: `CORRECT` → предлагаем GREEN, `INCORRECT` → YELLOW, `UNCERTAIN` → ничего, флаг «нужна проверка учителем». **ИИ не выставляет статус молча** — ученик/учитель подтверждают в один клик. Учитель всегда может переопределить.

## 2. Изменения в коде

### Prisma (новая модель)

```prisma
model SolutionSubmission {
  id               String   @id @default(cuid())
  studentId        String
  homeworkNumberId String
  files            StoredFile[]            // или отдельная join-таблица
  status           SubmissionStatus        // PENDING | CHECKING | DONE | FAILED
  verdict          SubmissionVerdict?      // CORRECT | INCORRECT | UNCERTAIN
  errorLocation    String?
  comment          String?
  confidence       Float?
  modelUsed        String?
  inputTokens      Int?
  outputTokens     Int?
  createdAt        DateTime @default(now())
  checkedAt        DateTime?

  @@index([studentId, homeworkNumberId])
}
```

### Файлы

- `lib/solution-check.ts` — клиент модели, сборка промпта, парсинг JSON, ретраи (1 повтор при невалидном JSON), fallback-модель.
- `lib/solution-check-queue.ts` — простая in-process очередь (последовательно, concurrency 1–2), чтобы не упереться в rate limit API.
- `app/api/solutions/route.ts` (POST — создать сабмит) + `app/api/solutions/[id]/route.ts` (GET — статус/результат). Это интерактивный fetch → API route, не server action (по конвенции проекта).
- Rate limit на отправку: `lib/rate-limit.ts`, например 10 сабмитов/час на ученика.
- После записи результата — `revalidateStudentTopicsData()` + `revalidateTeacherTopicsData()` + `revalidatePath`.
- Логирование: `solution.check.started / succeeded / failed / uncertain`.
- UI: блок в деталке номера у ученика (загрузка, спиннер «Проверяется…», результат); у учителя в деталке ученика — список сабмитов с фото и вердиктом ИИ.
- Env: `AI_CHECK_API_KEY`, `AI_CHECK_MODEL`, `AI_CHECK_FALLBACK_MODEL`, `AI_CHECK_ENABLED`.

### Ключевые принципы промпта

- Модель сначала **транскрибирует** рукописное решение в LaTeX, потом проверяет — так меньше галлюцинаций и транскрипцию видно учителю.
- Эталонный `answerLatex` даём модели, но просим проверять и ход решения, а не только совпадение ответа.
- Если фото нечитаемо / решение не по той задаче → `UNCERTAIN`, не гадать.
- Все комментарии по-русски.

## 3. Выбор модели

Требования: чтение рукописного русского текста + математики с фото, математическое рассуждение, structured output.

| Модель | Цена вход/выход, $/1M ток. | Комментарий |
|---|---|---|
| **Claude Sonnet 4.6** | 3 / 15 | Рекомендация: сильная математика и vision, надёжный structured output |
| Gemini 3.1 Pro | 2 / 12 | Отличное распознавание рукописного текста, хорошая альтернатива |
| GPT-5.4 | 2.5 / 15 | Сопоставим с Sonnet |
| Claude Haiku 4.5 | 1 / 5 | Дёшево, но слабее на кривом почерке и многошаговых решениях |
| Gemini 2.5 Flash | 0.3 / 2.5 | Самый дешёвый рабочий вариант, качество проверять на пилоте |

Стратегия: **начать с одной сильной модели (Sonnet 4.6 или Gemini 3.1 Pro)** — при 500 проверках/мес экономить на модели бессмысленно (см. бюджет). Двухступенчатую схему (дешёвая модель + эскалация сложных случаев на дорогую) имеет смысл вводить только после 3000+ проверок/мес.

Доступ: напрямую (Anthropic/Google) или через OpenRouter — одна интеграция, одна оплата, лёгкая смена модели. Для пилота OpenRouter удобнее.

## 4. Бюджет

Одна проверка ≈ 2 фото (~2×1200 ток.) + условие/ответ + инструкции ≈ **3000 ток. входа**, вердикт с разбором ≈ **1500 ток. выхода** (с запасом на рассуждение).

| Модель | $/проверка | 500 пров./мес | 3000 пров./мес |
|---|---|---|---|
| Claude Sonnet 4.6 | ~$0.031 | **~$16/мес** | ~$95/мес |
| Gemini 3.1 Pro | ~$0.024 | ~$12/мес | ~$72/мес |
| GPT-5.4 | ~$0.030 | ~$15/мес | ~$90/мес |
| Claude Haiku 4.5 | ~$0.011 | ~$5/мес | ~$32/мес |
| Gemini 2.5 Flash | ~$0.005 | ~$2.4/мес | ~$14/мес |

Вывод: на вашем объёме это **$5–20/мес** даже на топовых моделях. Prompt caching системной инструкции срежет ещё ~20–30% входа. Закладывать стоит ~$25/мес с запасом.

## 5. Риски и как их закрыть

- **Галлюцинации на плохом почерке** — порог `confidence`, вердикт `UNCERTAIN` вместо угадывания, транскрипция видна учителю.
- **ИИ ошибается в математике** — статус подтверждается человеком, учитель видит все сабмиты; на пилоте первые 2–4 недели учитель выборочно сверяет вердикты.
- **Ученик шлёт мусор/спам** — rate limit + лимит 3 фото ≤ 5 МБ.
- **API недоступен** — статус `FAILED` с кнопкой «Повторить», очередь не блокирует остальное.
- **Смена цен/моделей** — модель в env, слой `lib/solution-check.ts` изолирует провайдера.

## 6. План внедрения (≈ 4 этапа)

1. Схема + миграция + API загрузки сабмита (без ИИ) — учитель просто видит фото решений. Уже само по себе полезно.
2. `lib/solution-check.ts` + очередь + интеграция одной модели, вердикт в UI.
3. Автопредложение статуса светофора + SSE + вид для учителя.
4. Пилот: 2 недели сверки вердиктов учителем, подстройка промпта, затем решение о fallback/эскалации.
