## 2. Контекст проекта (проверь, что всё ещё так — документация могла отстать)

**TutorFlow** — платформа для репетитора/учителя с ИИ-помощником. Русскоязычный UI.
Учитель ведёт темы (теория, ДЗ, пронумерованные задачи), ученики отмечают прогресс светофором,
загружают фото решений, ИИ проверяет решения и подбирает задания на урок и на дом.

Стек: Next.js 15 (App Router + Server Actions) · React 19 · TypeScript strict · Node 20 ·
PostgreSQL + Prisma 5 · Tailwind 3 · собственная cookie-сессия (не NextAuth) · pino ·
@react-pdf/renderer · puppeteer-core (печатные PDF) · KaTeX.

Роли: **STUDENT**, **TEACHER**, **DEVELOPER** (дев-панель `/developer/panel`,
миграция `20260708150000_add_developer_role`).

Точки входа, с которых стоит начать:

- `CLAUDE.md` — карта архитектуры (17 КБ, читай целиком, это лучшая отправная точка).
- `AGENTS.md`, `README.md` — правила работы и запуск.
- `TZ_TutorFlow_MVP.md` — что система вообще должна делать (нужно, чтобы отличать
  «дыру» от «так задумано»).
- `middleware.ts` — единственный глобальный барьер.
- `lib/auth.ts`, `lib/password.ts`, `lib/password-policy.ts` — сессии и пароли.
- `lib/file-access.ts`, `app/files/[fileId]/route.ts`, `lib/storage.ts`,
  `lib/upload-validation.ts`, `lib/upload-file-name.ts` — файлы.
- `app/api/**/route.ts` — ~20 групп API-роутов (student, teacher, realtime, files).
- `actions/*.ts` — server actions (auth, topic, student, profile, group и др.).
- `lib/rate-limit.ts`, `lib/api-rate-limit.ts`, `lib/persistent-rate-limit.ts`.
- `lib/site-settings.ts` — key-value настройки через **raw SQL** (особое внимание).
- `prisma/schema.prisma` (~520 строк) и `prisma/migrations/`.
- `.github/workflows/`, `Dockerfile`, `docker-compose*.yml`, `next.config.ts`,

Особенность окружения: имя папки проекта — кириллица в форме NFD, часть утилит спотыкается
о путь. `npm run test` и `npm run build` могут не работать в контейнере — гоняй на хосте.

## 3. Как работать (методика, а не свободный поиск)

**Фаза A — разведка (не пиши находки, строй карту).**
Составь для себя: список всех точек входа (route handlers, server actions, middleware-маршруты,
SSE, файловые роуты, вебхуки), для каждой — кто может её вызвать по замыслу и какая проверка
это обеспечивает. Список всех моделей Prisma и того, кому принадлежит запись.
Эта карта потом идёт в отчёт как приложение «Карта поверхности атаки».

**Фаза B — систематическая проверка по чеклисту (раздел 4).**
Идёшь по чеклисту, не пропуская пункты. По каждому пункту фиксируешь либо находку,
либо явное «проверено, проблем не нашёл, смотрел вот это».

**Фаза C — подтверждение.**
Каждую находку, которую можно подтвердить на локальном стенде, — подтверждаешь: реальный
запрос, реальный ответ. Находка со статусом «подтверждено эксплойтом» стоит в десять раз больше,
чем «в коде выглядит подозрительно».

**Фаза D — самопроверка на ложные срабатывания.**
Перед тем как записать находку, ответь себе: нет ли защиты выше по стеку, которую я не заметил
(middleware, `requireUser`, проверка в `lib/`, ограничение Prisma, CSP, ограничение Next.js)?
Если не проверил — проверь. Если находка не выдерживает — выкинь её или понизь до «гипотеза».

**Фаза E — отчёт.**

## 4. Чеклист (обязательный минимум; расширяй, если увидишь что-то ещё)

### 4.1 Аутентификация
- Формат и энтропия токена сессии, хранение (sha256), сравнение (timing-safe?).
- Хэш пароля (scrypt): параметры, соль, сравнение.
- Политика паролей, длина, ограничения, можно ли поставить пустой/слабый.
- Перебор пароля: есть ли лимит, по чему он считается (IP? email?), можно ли обойти.
- Перечисление пользователей (разные ответы/тайминги для существующего и несуществующего email).
- Смена пароля: требуется ли текущий, инвалидируются ли остальные сессии.
- Выход: реально ли убивается токен на сервере или только cookie у клиента.

### 4.2 Авторизация и IDOR
- Для **каждого** API-роута и server action: проверяется ли роль и **владение объектом**.
  Ученик, подставляющий чужой `studentId` / `topicId` / `homeworkId` / `lessonId` /
  `submissionId` / `fileId` — получает ли данные.
- Учитель против учителя (если в системе может быть больше одного) — видит ли чужих учеников.
- Роль DEVELOPER: что именно она открывает, можно ли до неё дотянуться обычному пользователю,
  можно ли повысить себе роль через обновление профиля.
- `middleware.ts` проверяет только наличие сессии — найди маршруты, где на этом всё и заканчивается.
- Проверь, не полагается ли где-то авторизация на данные из клиента (скрытое поле формы, тело JSON).

### 4.3 Административные и дев-функции
- `/developer/panel` и всё, что оттуда управляется (`lib/site-settings.ts`): кто может читать
  и писать настройки, валидируются ли значения, можно ли настройкой сломать безопасность
  (например, снизить лимиты, переключить хранилище, отключить проверки).
- Батчевые операции из дев-панели: объём, лимиты, идемпотентность.
- Есть ли отладочные роуты/флаги/логи, которые доживают до продакшена.

### 4.4 Сессии, cookie
- Флаги cookie `tutor_session`: HttpOnly, Secure, SameSite, Path, Max-Age.
- Срок жизни сессии, ротация после логина (session fixation), ограничение числа сессий.
- Где ещё хранится состояние клиента (localStorage и т.п.) и что там лежит.
- JWT в проекте, судя по описанию, нет — **проверь это**, а не поверь на слово; если есть,
  разбери алгоритм, проверку подписи, `alg:none`, срок, аудиторию.

### 4.5 Восстановление пароля
- Есть ли вообще механизм. Если есть — энтропия и срок жизни токена, одноразовость,
  привязка к пользователю, утечка токена в логи/referer, возможность перечисления.
- Если нет — как учитель сбрасывает пароль ученику: не даёт ли это захват аккаунта.

### 4.6 Инъекции
- Все места с raw SQL (`$queryRaw`, `$executeRaw`, `$queryRawUnsafe`) — начни с `lib/site-settings.ts`.
  Параметризованы ли, где строится SQL конкатенацией.
- Prisma-фильтры, собираемые из пользовательского ввода (сортировка, поиск, `contains`).
- Поиск по номерам, импорт темы из JSON (`lib/topic-import.ts`,
  `app/api/teacher/topic-import/route.ts`) — что происходит с недоверенным JSON.
- **Prompt injection** как отдельный класс: пользовательский текст (заметки ученика, названия тем,
  распознанный текст с фото) уходит в промпты ИИ (`lib/lesson-plan-generate.ts`,
  `lib/homework-plan-generate.ts`, `lib/solution-check*.ts`). Может ли ученик текстом на фото
  или в заметке заставить ИИ поставить себе зелёный статус, слить системный промпт,
  сжечь бюджет? Разбери, как парсится ответ модели (`lib/solution-check-parse.ts`) и что будет
  с враждебным ответом.

### 4.7 XSS, CSRF, SSRF
- Все `dangerouslySetInnerHTML`, вставка HTML в PDF/печатную раздатку
  (`lib/lesson-print-html.ts`, `lib/print-theme.ts`), рендер KaTeX из пользовательского LaTeX
  (условия и ответы к номерам) — можно ли протащить скрипт или сломать рендер.
- CSP и прочие заголовки: есть ли, что реально выставляется на ответах.
- CSRF: Next server actions имеют встроенную защиту — проверь, что она не отключена и что
  **API-роуты** (обычный `fetch`/JSON) не выполняют изменяющие операции без защиты;
  проверь `SameSite` и наличие проверки Origin.
- SSRF: любые места, где сервер ходит по URL, который влияет пользователь — puppeteer-рендер,
  загрузка изображений, `sharp`, `pdfjs-dist`, вызовы внешних API.

### 4.8 Загрузка файлов
- `lib/upload-validation.ts`, `lib/upload-file-name.ts`, `app/api/teacher/uploads`,
  фото решений учеников (`app/api/student/homework-submissions`).
- Проверка типа: по расширению или по содержимому; можно ли загрузить polyglot/SVG/HTML.
- Лимит размера (в `next.config.ts` заявлено 15 МБ на server action) — соблюдается ли для API-роутов.
- Path traversal в имени файла, коллизии имён, перезапись чужих файлов.
- Раздача: `app/files/[fileId]/route.ts` + `lib/file-access.ts` — может ли ученик скачать
  чужое фото/чужой файл; какие заголовки отдаются (`Content-Type`, `Content-Disposition`,
  `X-Content-Type-Options`); можно ли получить XSS через отдачу файла.
- Хранение: три бэкенда (`local:`/`s3:`/`blob:`) — права доступа к бакету, публичность объектов,
  можно ли угадать ключ.
- Ретеншн фото (`lib/homework-photo-retention*.ts`): реально ли удаляются, откуда, есть ли гонка.

### 4.9 CORS и заголовки безопасности
- Что настроено в `next.config.ts` / `middleware.ts`, отражается ли Origin, стоит ли
  `Access-Control-Allow-Credentials`.
- HSTS, X-Frame-Options / frame-ancestors, Referrer-Policy, Permissions-Policy.
- SSE-эндпоинт `/api/realtime` — отдельно: кто на него может подписаться, какие события
  утекают подписчику, не приходят ли ученику события про других учеников.

### 4.10 Секреты и конфигурация
- `.env`, `.env.production`, `.env.example` — что реально лежит, что попало в git
  (`git log -p -- .env*`), что попадает в клиентский бандл (`NEXT_PUBLIC_*`).
- Ключи в коде, в тестах, в сидах (`prisma/seed.ts` — сидовые пароли `teacher123`/`student123`:
  что будет, если сид уедет в прод).
- `Dockerfile`, `docker-compose*.yml`: секреты в слоях, root-пользователь, открытые порты.
- `.github/workflows/*`: доступ к секретам, `pull_request_target`, запуск чужого кода,
  логирование секретов, права `GITHUB_TOKEN`.

### 4.11 Зависимости и supply chain
- `npm audit` — но **не переписывай его вывод в отчёт**. Для каждой значимой уязвимости
  ответь: используется ли уязвимый путь кода в этом проекте вообще.
- Зафиксированы ли версии (`^` во всех зависимостях + наличие `package-lock.json`),
  есть ли `npm ci` в CI и в Dockerfile.
- Постустановочные скрипты (`postinstall: prisma generate`), подозрительные транзитивные пакеты.
- `puppeteer-core` + системный Chromium: откуда берётся бинарь, кто его контролирует.

### 4.12 Вебхуки и внешние интеграции
- Есть ли входящие вебхуки; если да — проверка подписи, защита от повтора, идемпотентность.
- Исходящие вызовы ИИ-провайдера: где хранится ключ, попадает ли он в логи, есть ли таймаут
  и ограничение стоимости, что происходит при ответе-мусоре.

### 4.13 Rate limiting и злоупотребления
- Три реализации лимитов (`rate-limit`, `api-rate-limit`, `persistent-rate-limit`) — где какая
  применяется, а где не применяется вовсе.
- In-memory лимиты при нескольких инстансах/перезапуске pm2 — обходятся ли.
- Сценарии, которые стоят денег: ИИ-проверка решений, ИИ-подбор урока и ДЗ, генерация PDF
  через Chromium, экспорт отчётов. Может ли один ученик исчерпать бюджет всей платформы?
  Может ли учитель случайно?
- Спам и накрутка: массовая отправка фото, накрутка стрика (`lib/student-streak.ts`),
  массовое изменение статусов, создание учеников/групп/уроков пачками.
- Массовый парсинг: может ли залогиненный ученик выкачать все темы, условия, ответы

- Есть ли защита от автоматизации на логине (капча/задержка) и нужна ли она.

### 4.14 Персональные данные
- Что вообще хранится о несовершеннолетних учениках: имена, email, фото работ, заметки учителя,

- Удаление ученика — реально ли удаляются его данные и файлы, или остаются осиротевшие записи.
- Экспорт данных (`lib/student-export-data.ts`, PDF-отчёт) — кто может его получить.

## 5. Формат отчёта

Файл: `.planning/audit-2026-08-03/reports/01-security-report.md`.

Структура:

1. **Резюме для владельца** (не более страницы): в каком состоянии безопасность,
   3–7 главных выводов человеческим языком, можно ли в таком виде пускать реальных школьников.
2. **Сводная таблица находок**: ID · Заголовок · Критичность · Уверенность · Где.
3. **Находки** — по одной секции на каждую, отсортированы по критичности:

```
### SEC-001 — <короткий заголовок>

- **Критичность:** CRITICAL | HIGH | MEDIUM | LOW
- **Уверенность:** подтверждено эксплойтом | подтверждено чтением кода | гипотеза
- **Где:** путь/файл.ts:120-138 (и все связанные места)
- **Кто может это использовать:** аноним | залогиненный ученик | учитель | нужен доступ к БД

**Суть.** Что именно не так, механика в 3–6 предложениях.

**Воспроизведение.** Пошагово, с конкретным запросом/командой и наблюдаемым результатом.
Если подтвердить не удалось — честно: «не воспроизводил, потому что …».

**Последствие для TutorFlow.** Что конкретно теряется: чьи данные, какие деньги,
какой репутационный эффект. Без общих слов вроде «компрометация системы».

**Почему это не ложное срабатывание.** Какие защиты выше по стеку ты проверил и исключил.

**Оценка трудоёмкости исправления.** S / M / L и одна фраза о направлении.
Само исправление НЕ пишешь.
```

4. **Проверено, проблем не найдено** — список пунктов чеклиста с одной строкой,
   что именно смотрел. Это важнее, чем кажется: показывает глубину покрытия.
5. **Что осталось непроверенным и почему** — честно.
6. **Приложение: карта поверхности атаки** — таблица «точка входа → кто вызывает по замыслу →
   чем это обеспечено».
7. **Приложение: инвентарь секретов** — где какие секреты лежат (без значений).

Критичность определяй по последствию для этого продукта, а не по абстрактной шкале.
Захват чужого аккаунта ученика или чтение чужих фото — CRITICAL. Отсутствующий
security-header без доказанного вектора — LOW, и не притворяйся, что это больше.
