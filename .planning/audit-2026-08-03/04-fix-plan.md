## Принципы

1. Одна волна = одна ветка = один смысловой блок.
2. Миграции только вручную: `prisma/migrations/<timestamp>_<name>/migration.sql` + `prisma migrate deploy`. Никакого `migrate dev` и `db push`.
3. Правка `lib/` → тест в `tests/`.
4. Разрушающая операция сначала считает и называет последствия, потом требует отдельного подтверждения.
5. Проверка волны: `npx prisma generate && npx tsc --noEmit && npm run lint && npm run test && npm run build` на Маке. В облаке и в локальной VM работает только eslint и чистые тесты — `prisma generate` упирается в заблокированный `binaries.prisma.sh`, `tsx` в VM не стартует (esbuild собран под macOS).

## Волна 1 — потеря данных ✅ сделано (в редакции 2)

### PROD-001 — отмена ДЗ

Решение владельца: удалять по-настоящему. Мягкая отмена (`cancelledAt`) из первой редакции откачена целиком.

Что сделано вместо неё — **честный диалог**. Он теперь считает и называет: «безвозвратно удалятся присланные учеником файлы: фото решений — N, результаты ИИ-проверок — M. Скачать их потом будет неоткуда». Плюс отдельной строкой, что выставленные статусы сохранятся. Старый текст обещал только снятие дедлайнов.

### ARCH-011 — зеркало дедлайнов

Это была настоящая порча данных, и она чинится независимо от предыдущего пункта.

Дедлайн живёт в двух местах: на `HomeworkAssignment` и продублирован на паре (ученик, номер) — оттуда его читают календарь ученика, метки просрочки и PDF-отчёт. Пара может быть одна, а номер теперь может входить в несколько ДЗ. Раньше выдача просто перезаписывала поле, а отмена гасила его по совпадению значения — из-за чего отмена одного ДЗ снимала срок у другого.

`lib/homework-deadline-mirror.ts`: правильное значение зеркала — **ближайший дедлайн среди всех ДЗ, где номер есть**. Пересчёт вызывается и после выдачи, и после отмены; источник истины один — набор существующих `HomeworkAssignment`. 11 тестов, включая регрессию на «отмена одного ДЗ оставляет дедлайн второго».

### Правило повторной выдачи

Было: блокировался любой когда-либо выданный номер — перевыдать нерешённое было нельзя без отмены старого ДЗ.
Стало: блокируются только **решённые** — GREEN (решил сразу) и YELLOW (решил после самопроверки). Красный и неотмеченный выдаются заново, это основной сценарий «дай перерешать». Сообщение: «Номер N ученик уже решил — повторно его не выдаём».

### PROD-002 — замена строки «Номера»

`lib/topic-numbers-change.ts` (чистая логика, 14 тестов) считает по каждому исчезающему номеру, что за ним стоит: статусы, заметки, дедлайны, выданные ДЗ, вердикты ИИ, пункты уроков, LaTeX-условия и ответы. `/api/teacher/topic-numbers-preview` показывает это перед сохранением списком вида «№ 302 — статус у 3 учеников, входит в 2 активных ДЗ, условие и ответ». Номера из выданных ДЗ требуют отдельной галочки.

Защита серверная: `updateTopicAction` пересчитывает план заново и отклоняет сохранение, если подтверждение не покрывает опасные номера или устарело. UI работает fail-open (сеть отвалилась — форму всё равно отправляем), сервер fail-closed.

### ARCH-013 — удаление темы

Диалог называет последствия цифрами вместо «и статусами по номерам». Экшен сверяет присланное подтверждение с текущим состоянием: если с момента открытия страницы объём работы изменился — человек видел не те последствия, и удаление отклоняется.

Архивирование тем (`Topic.archivedAt`) отложено: задевает 12+ мест чтения.

## Волна 2 — целостность автопроверки

### SEC-001 (HIGH) — ученик ставит себе GREEN надписью на фото

`injectionSuspected` сохраняется, но `applyVerdictsToProgress` его не смотрит. Порог `confidence` не помогает: значение возвращает сама модель.

Три слоя, все серверные:

1. `injectionSuspected === true` → жёсткий гейт: статус не пишется, вердикт помечается «нужна проверка учителем».
2. Автоматический GREEN только при серверной сверке `recognizedAnswer` с `answerLatex` (нормализация пробелов, скобок, десятичных разделителей). Не совпало — жёлтый или на проверку учителю. Модель больше не решает сама, что задача решена.
3. Санитарная проверка: `confidence` ровно `1.0` вместе с текстовыми маркерами инструкций в распознанном тексте понижает доверие, а не повышает.

Тесты: набор инъекционных ответов модели, ни один не даёт GREEN.

### SEC-005 — эталонный ответ утекает через вывод проверки

Серверная редактура: если `recognizedAnswer` или `comment` совпадает с `answerLatex` после нормализации — ученику не показываем, учителю показываем.

### SEC-006 + PROD-010 — бюджет ИИ

Глобальный дневной бюджет списывается вплотную к `enqueue`, после того как транзакция подтвердила реальное ДЗ с фото и номерами. При `FAILED` — возврат слота. Почасовой лимит на ученика остаётся до валидации: он как раз защищает от долбёжки.

### PROD-011 — «не распознано» рядом с «Верно.»

При уверенности ниже порога комментарий модели не показывается как утверждение.
