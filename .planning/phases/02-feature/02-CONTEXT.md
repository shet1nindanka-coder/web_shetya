**Gathered:** 2026-08-21

<domain>
## Phase Boundary

Ежемесячные звонки родителям учеников. Учитель видит, кому пора позвонить (отсчёт
от последнего УСПЕШНОГО звонка по каждому ученику), фиксирует состоявшийся звонок
с комментарием в свободной форме, может отметить неудачную попытку (не закрывает
напоминание). История звонков по ученику накапливается. Доступ к записям: учитель
(владелец ученика, `User.teacherId`) и все пользователи роли DEVELOPER; ученики и
чужие учителя не видят ничего — контроль на уровне API. Комментарии — персональные
данные, в логи не пишутся.

</domain>

<decisions>
## Implementation Decisions

### Модель напоминания
- Якорь: дата последнего звонка с исходом REACHED; если успешных звонков не было —
  дата создания ученика (новому ученику нужно позвонить в течение первого месяца).
- Периодичность: 30 дней от якоря («раз в месяц» = скользящие 30 дней, а не календарный месяц).
- Состояния: `ok` (< 30 дней) → «пора позвонить» (30–45 дней) → «просрочено» (≥ 45 дней,
  то есть 2+ недели сверх срока).
- Неудачная попытка (NO_ANSWER) не двигает якорь, но показывается в истории и в карточке
  («попытка N дней назад») — учитель видит, что пытался.

### Уведомления
- Переиспользуется существующая модель `Notification` + колокольчик; для учителя
  добавляется общий endpoint уведомлений (существующий — STUDENT-only).
- Уведомление PARENT_CALL_DUE создаётся лениво при обращении учителя к уведомлениям
  или разделу «звонки»: дедупликация — не больше одного уведомления на пару
  (учитель, ученик) в рамках одного «периода задолженности» (createdAt > якоря).
- После успешного звонка непрочитанные PARENT_CALL_DUE по этому ученику помечаются
  прочитанными.

### Интерфейс
- Отдельная вкладка «звонки» в навигации учителя (`/teacher/calls`); разработчик видит
  тот же раздел через `/developer/calls` (rewrite уже существует) со всеми учениками
  всех учителей и колонкой учителя.
- Страница: список учеников с состоянием (просрочено → пора → недавно созвонились),
  форма фиксации звонка (исход: дозвонился / не дозвонился + комментарий), история
  звонков по ученику (раскрывающаяся).
- Пустое состояние (учеников нет) и состояние «всем позвонили недавно» — обязательны.
- Запись звонка = API route (интерактивный fetch, как дедлайны), чтение — server component
  через lib (конвенция репо).

### Данные
- Новая модель `ParentCallLog`: studentId (FK User, Cascade), teacherId (FK User, SetNull,
  nullable — лог переживает удаление учителя), outcome (enum REACHED | NO_ANSWER),
  comment (Text, nullable), calledAt (default now).
- Миграция — только новая, рукописная (`prisma/migrations/<ts>_add_parent_call_log/migration.sql`),
  применение `migrate deploy`; существующие миграции не трогаются.
- Никакого удаления/редактирования записей в MVP: история append-only (требование
  «сохраняется, а не перезаписывается»). Удаление ученика каскадно удаляет его логи.

### Безопасность
- API: TEACHER — только свои ученики (`student.teacherId === user.id`); DEVELOPER — все;
  остальные роли — 401/403. Проверка в каждом route-handler'е.
- Комментарии не попадают в pino-логи (логируются только id), не отдаются в
  student-facing ответах нигде.

### Claude's Discretion
- Точные формулировки статусов и уведомлений — по скиллу design:ux-copy на этапе вёрстки.
- Порядок сортировки и детали компоновки — в рамках дизайн-системы ШБЗ (см. UI-SPEC).

</decisions>

<specifics>
## Specific Ideas

- Светофорная семантика уже занята статусами задач; статусы звонков должны читаться
  иначе (например, чипы «просрочено» в красной паре допустимы — это прямой сигнал,
  но не вводить новые цвета мимо токенов).
- Телефоны родителей в системе не хранятся — раздел фиксирует факт и содержание
  звонка, не контакты.

</specifics>
